# 15. 3Sum

## Problem

Given an integer array `nums`, return all the triplets `[nums[i], nums[j], nums[k]]` such that `i != j`, `i != k`, `j != k`, and `nums[i] + nums[j] + nums[k] == 0`.

The catch is that the answer must not contain duplicate triplets — the *values* in the triplets matter, not their original positions.

**Examples:**

| Input | Output |
|-------|--------|
| `[-1, 0, 1, 2, -1, -4]` | `[[-1, -1, 2], [-1, 0, 1]]` |
| `[0, 1, 1]` | `[]` |
| `[0, 0, 0]` | `[[0, 0, 0]]` |

**Constraints:**

- `3 <= nums.length <= 3000`
- `-10^5 <= nums[i] <= 10^5`

[LeetCode Link](https://leetcode.com/problems/3sum/)

---

## Intuition

The brute force version is the obvious one: three nested loops, every triplet, check the sum, dedupe afterwards. That's `O(n^3)` and the deduping is its own headache because the same values can appear at different indices.

There's a much nicer way once you notice that 3Sum is really a stack of 2Sum problems in disguise. If you fix the first number `a`, then you need two more numbers in the rest of the array that sum to `-a`. And **2Sum on a sorted array** has a beautiful two-pointer solution: one pointer at the front, one at the back, move them inward based on whether the current sum is too small or too big. That gives you 3Sum in `O(n^2)` total — `n` choices for the fixed element, `O(n)` work for each two-pointer sweep.

Sorting also makes the duplicate problem tractable. Once equal values sit next to each other, "skip duplicates" turns into "skip while the next neighbor is the same" — no hash sets needed.

---

## Approach: Sort + Fixed Pivot + Two Pointers — O(n²)

### The Big Picture

1. Sort `nums` ascending.
2. Walk `i` from the left. The value at `i` is the "pivot" — the first number of every triplet we'll try with this pivot.
3. For each `i`, run two pointers on the slice to the right of `i`: `left = i + 1`, `right = n - 1`. Slide them toward each other looking for `nums[left] + nums[right] == -nums[i]`.
4. Skip duplicate values for `i`, `left`, and `right` so the same triplet never gets reported twice.

The whole solution is one outer `for` loop wrapping a two-pointer `while` loop.

### Why Sorting Earns Its Keep

Sorting costs `O(n log n)`, which is dominated by the outer loop anyway, so it's free in big-O terms. In return it buys you three things at once:

- **Two pointers work.** On a sorted array, increasing `left` only makes the sum bigger, decreasing `right` only makes it smaller. That's the monotonicity that lets the pointers converge in linear time.
- **Easy duplicate handling.** Equal values are adjacent — skipping them is just `while nums[i] == nums[i-1] { i += 1 }`.
- **Early termination.** Once the smallest possible triple at index `i` (which is `nums[i] + nums[i+1] + nums[i+2]`) is already positive, every later pivot is even larger, so no further triple can sum to zero. We `break`.

### Algorithm

```
sort nums
for i in 0..n-2:
    if i > 0 and nums[i] == nums[i-1]: continue       # dedupe pivot
    if nums[i] + nums[i+1] + nums[i+2] > 0: break     # smallest triple at i already too big

    left, right = i+1, n-1
    while left < right:
        s = nums[i] + nums[left] + nums[right]
        if s == 0:
            push [nums[i], nums[left], nums[right]]
            while left < right and nums[left]  == nums[left+1]:  left  += 1
            while left < right and nums[right] == nums[right-1]: right -= 1
            left  += 1
            right -= 1
        elif s < 0:
            left  += 1
        else:
            right -= 1
return result
```

The two inner `while` loops after a successful match are the de-dupe step for `left` and `right`. They walk the pointers across any plateau of equal values, then the trailing `left += 1; right -= 1` finally moves them off that plateau onto fresh values.

---

### Why Does This Work?

The correctness argument has three pieces — completeness, no duplicates, and the early-break shortcut.

**Completeness.** Every zero-sum triplet `(a, b, c)` with `a ≤ b ≤ c` (the sorted form) appears in the output exactly when the outer loop visits the index of its smallest value. At that point the two pointers start at the full remaining range and converge. The two-pointer invariant is the classic 2Sum one: if the current sum is too small, the only way to grow it without losing any candidate pair is to bump `left`; if it's too big, bump `right` down. No valid pair gets skipped because the pair we just rejected couldn't satisfy the target with anything we walked past.

**No duplicates.** Three guards do the work:

- `if i > 0 && nums[i] == nums[i-1]: continue` — the same pivot value is never used twice.
- After a hit, the two `while` loops on `left` and `right` skip over runs of equal neighbors before the next iteration. This stops emitting `[a, b, c]` again from a different copy of `b` or `c`.
- The pointers are otherwise strictly moving inward, so the same `(left, right)` pair is never visited twice.

**Early termination.** Because the array is sorted, `nums[i] + nums[i+1] + nums[i+2]` is the *smallest* sum any triplet starting at index `i` can produce. If that already exceeds zero, every later `i` only makes things worse. `break` is safe.

### Edge Cases

| Case | Behavior |
|------|----------|
| `nums.len() < 3` | Early return with empty vector. |
| All zeros (`[0,0,0,0]`) | Pivot at `i=0` finds `[0,0,0]` once. The plateau-skip walks `left` and `right` through the remaining zeros so the same triplet isn't emitted again. The pivot dedupe then continues past every other 0. Returns `[[0,0,0]]`. |
| All positive (`[1,2,3,4,5]`) | First pivot's smallest triple `1+2+3 = 6 > 0` → early break. Returns `[]`. |
| All negative (`[-5,-4,-3,-2,-1]`) | Outer loop runs all the way; every two-pointer sweep exits with sum still negative. Returns `[]`. |
| Many duplicates | Pivot dedupe + post-hit plateau skips ensure each distinct triplet appears once. |

### Complexity

| | |
|---|---|
| **Time** | O(n²). The sort costs O(n log n). The outer loop is O(n) and each inner two-pointer sweep is O(n), giving O(n²) for the main work. |
| **Space** | O(1) extra beyond the output (ignoring sort's auxiliary memory, which is O(log n) for Rust's sort). The result vector itself is bounded by O(n²) in the worst case. |
